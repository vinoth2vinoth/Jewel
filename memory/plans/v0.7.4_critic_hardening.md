# Design Plan: Jewel v0.7.4 - Critic Hardening, Test Modification Policy, and Domain Sanity Checks

We will harden Jewel's validation engine to protect existing test code, strengthen LLM retry controls, incorporate a deterministic matrix critic, and separate failure types precisely.

---

## 1. Objectives & Phases

### Phase 1: Test Modification Policy
- Create `src/verification/test-change-policy.ts` to detect whether a patch modifies existing test files invasively or only appends to them.
- Detect modified test names, assertions, and bodies. Allow new imports for appended tests (warning only).

### Phase 2: Preserve-Existing-Tests Contract Field
- Detect `"preserveExistingTests": true` in prompt text if it contains "keep existing tests exactly as they are".
- Track this field in `TaskContract` schema.
- Validate patches against this policy before verification. If violated, fail with status `EXISTING_TEST_MODIFIED`.

### Phase 3: Test Provenance Reporting
- Create `src/verification/test-provenance.ts`.
- Save detailed provenance reports in `.jewel/reports/test-provenance.json` and `.jewel/reports/test-provenance.md`, and link them in `latest-run.md`.

### Phase 4: Correctness Critic Hardening
- Expand critic output schema to include: `verdict`, `confidence`, `explanation`, `suspectedRootCause`, `suggestedFix`, `canAutoRetry`, `requiresHumanReview`.
- Enforce strict retry constraints: only retry if `canAutoRetry` is true and confidence is `high`. Exit with `NEEDS_HUMAN_REVIEW` if confidence is medium/low or verdict is `UNKNOWN`. Exit with `RETRY_LIMIT_REACHED` if same failure occurs twice.

### Phase 5: Matrix Dimension Sanity Critic
- Implement `src/verification/domain-critics/matrix-critic.ts` to deterministic-check matrix test logic (specifically multiplying dimensions constraints like $2\times2 \times 2\times3$ expected to throw).

### Phase 6: Bounded Retry Policy
- Create `src/core/retry-policy.ts` to implement hard retry stops (repeated failure signature, repeated verdict, low confidence, safety/path/policy violations, rollback failure).

### Phase 7: Repair Feedback Injection
- Update provider prompt builder to include detailed critic feedback, allowed files scope, and test protection instructions on retry.

### Phase 8: Hardened Statuses
- Track and report: `GENERATED_TEST_SUSPECT`, `EXISTING_TEST_MODIFIED`, `NEEDS_HUMAN_REVIEW`, `RETRY_LIMIT_REACHED`, `FLAKY_TEST_SUSPECT`, `DOMAIN_RULE_VIOLATION`.

### Phase 9: Automated Unit and E2E Tests
- Implement rigorous verification tests.

---

## 2. File Implementation Details

### `src/verification/test-change-policy.ts`
- Use TypeScript AST parsing via `typescript` compiler module.
- Parse original test file and patched test file.
- Compare imports, test name lists, and test bodies.
- Return `{ success: boolean, invasive: boolean, findings: string[], appendOnly: boolean }`.

### `src/verification/test-provenance.ts`
- Generate JSON and MD reports recording test name changes, append status, critic verdicts, and provenance metadata.

### `src/verification/domain-critics/matrix-critic.ts`
- Scan diff or files for matrix constructor/multiply calls. Extract dimension numbers. Check compatibility.
- Return `{ status: 'PASS' | 'FAIL', verdict?: string, reason?: string }`.

### `src/core/retry-policy.ts`
- Track execution history. Compute MD5 signature of test outputs. Check for duplicates. Stop early when required.
