# Design Plan: Jewel v0.9.0 Phase 4 - Local Web UI Dashboard

We will implement Phase 4 of the Jewel v0.9.0 roadmap: **Local Web UI Dashboard**. This provides a stunning, glassy web interface with real-time updates and interactive controls, allowing developers to monitor task execution, review file diffs, see critic feedback, and approve/reject/retry patches directly in the browser using core Node.js modules without adding any external packages.

---

## 1. Affected Files

1. **`src/cli/index.ts`**:
   - Add support for `--ui` flag in `printHelp()` output.
   - Update the `run` command routing block: parse `--ui` flag into a boolean `uiFlag` and pass it as the final argument to `runTask()`.
     - Update the call: `await runTask(taskText, filesNeeded, useMock, process.cwd(), yesFlag, noReview, keepFailed, overrides, dryRun, uiFlag);`.
   - Update the `verify` command switch case: change it to `await runVerify();` (since `runVerify` will become asynchronous) to prevent premature CLI exit. Capture any thrown errors and handle exit codes cleanly inside `main()`.

2. **`src/cli/commands/verify.ts`**:
   - Refactor `runVerify` to be an asynchronous function (`async runVerify()`).
   - Await `runVerification` execution: `const report = await runVerification(config, cwd)`.
   - Remove any direct calls to `process.exit()`. If verification fails, return a failure status or throw an error, letting the main CLI coordinator handle the exit.

3. **`src/cli/commands/run.ts`**:
   - Update `runTask()` signature to accept `useUI: boolean = false` as the final parameter:
     ```typescript
     export async function runTask(
       task: string,
       filesNeeded: string[] = [],
       useMock: boolean = false,
       cwd: string = process.cwd(),
       yesFlag: boolean = false,
       noReview: boolean = false,
       keepFailed: boolean = false,
       cliOverrides?: {
         provider?: string;
         model?: string;
         temperature?: number;
         maxOutputTokens?: number;
       },
       dryRun: boolean = false,
       useUI: boolean = false
     ): Promise<void>
     ```
   - Declare `let uiServer: UIServer | null = null;` at the top of the function.
   - If `useUI` is `true`, immediately instantiate `uiServer` and start it:
     ```typescript
     uiServer = new UIServer({ startPort: 3000 });
     await uiServer.start();
     console.log(`\n[+] Dashboard server started. View live progress at: ${uiServer.getUrl()}`);
     ```
   - Update the `runVerification` call: change it to `await runVerification(config, cwd, onProgressCallback)`.
   - Implement conditional interactive prompts:
     - If `useUI` is `false`, keep the original CLI `askQuestion` stdin prompts.
     - If `useUI` is `true`, redirect all approval steps to `uiServer.waitForApproval(promptType)` (which returns `Promise<{ action: 'approve' | 'reject' | 'retry' | 'override' | 'abort'; comment?: string }>`):
       - Scope expansion: `await uiServer.waitForApproval('scope-expansion')`
       - Patch diff review: `await uiServer.waitForApproval('patch-review')`
       - Retry choice: `await uiServer.waitForApproval('retry-choice')`
   - Map UI actions to CLI retry choices cleanly:
     - `'retry'` maps to `'r'` (setting `customHint = comment`)
     - `'override'` maps to `'o'`
     - `'abort'` maps to `'a'` (default)
     - Adapt conditional loops in `runTask` to check for both string values (e.g. `choice === 'r' || choice === 'retry'`).
   - Refactor `runTask` exit routing:
     - Wrap the execution logic in a `try-catch-finally` block.
     - Do not call `process.exit()` directly inside the `try` or `catch` blocks or any helper routes (including early returns like empty descriptions or dry-run branches).
     - Save any target exit code (`let exitCode: number | null = null;`) or thrown errors (`let exitError: any = null;`).
     - If an exception or `JewelError` is caught:
       - If `useUI` is active, update the UI state to stage `'failed'`, include the error in `findings`, print a clear notice to the terminal, and wait for exit confirmation (`await waitForExitAcknowledgment(uiServer)`) *before* letting the error propagate or assigning the final failure exit code.
       - Otherwise, let the error propagate immediately.
     - If execution completes successfully, update the state to stage `'completed'`.
     - At the end of a successful run loop, check `if (useUI && uiServer)`:
       - Print a terminal notice: `"Dashboard execution finished. Open ${uiServer.getUrl()} to stop the server and inspect results, or press [ENTER] in this terminal to exit."`
       - Wait for user acknowledgment using a CLI `readline` listener or UI exit resolution. Do not call `process.exit(0)` directly before awaiting this acknowledgment.
     - In the `finally` block, guarantee server cleanup:
       - If `uiServer` is instantiated, call `await uiServer.close();`.
       - After server cleanup, if there is a pending `exitError`, **throw it first** to let it propagate to `main()`.
       - If there is no pending `exitError` but `exitCode` is set, call `process.exit(exitCode)`.

4. **`src/verification/runner.ts`**:
   - Refactor `runVerification` to be an asynchronous function (`async runVerification`) that returns `Promise<VerificationReport>`.
   - Execute verification commands **sequentially** in a `for` loop (avoiding parallel execution to prevent interleaved outputs and race conditions).
   - Wrap command executions inside the loop in a `try-catch` block: if a command fails to spawn or throws an execution exception, capture it cleanly as a `'FAIL'` with exit code `99` and continue the loop rather than crashing early.
   - Standardize host execution on `cp.spawn` with `{ shell: true }` instead of `cp.exec` to stream logs directly and avoid the `maxBuffer exceeded` memory limit which causes crashes on large test reports.
   - Accept an optional progress callback `onProgress?: (progress: { key: string, stdout: string, stderr: string, status: 'RUNNING' | 'PASS' | 'FAIL' | 'BLOCKED' | 'SKIPPED' }) => void`. Stream live stdout/stderr chunk updates through this callback, ensuring all statuses are handled.
   - Refactor `dockerUtils.executeDocker` to run the Docker process asynchronously using `cp.spawn` (without `{ shell: true }` to maintain security and avoid backslash escaping issues on Windows) and return a Promise:
     ```typescript
     executeDocker(
       args: string[],
       cwd: string,
       env: Record<string, string | undefined>,
       onChunk?: (chunk: string, type: 'stdout' | 'stderr') => void
     ): Promise<{ status: number | null; signal: string | null; stdout: string; stderr: string; error?: Error }>
     ```
     Pipes stdout/stderr streams to `onChunk` for real-time progress updates, accumulating stdout/stderr buffers to resolve on process close.
   - Add single-resolution guards (`let completed = false;`) inside the async runner and Docker promises to prevent multiple resolver/rejecter calls if both `close` and `error` events trigger.

6. **`src/cli/ui-server.ts`** *(New File)*:
   - Implement the `UIServer` class using Node's standard `http` module.
   - The constructor (or the `start` function) accepts an optional `startPort` parameter (defaulting to 3000) to allow tests to specify custom ports or port `0` for ephemeral binds.
   - Generate a cryptographically secure, session-scoped token using `crypto.randomUUID()` when the server starts. The token remains valid for the entire duration of the dashboard server run.
   - Define the `UIState` interface and public `updateState(partial: Partial<UIState>): void` API on `UIServer` to feed state updates from `runTask()`.
   - Expose the dashboard HTML page at `GET /` and `/index.html` (loaded from `DASHBOARD_HTML` constant in `src/cli/dashboard-html.ts` to ensure it packages cleanly with TypeScript without copying tasks).
   - Implement validation middleware for all routes (including static files `GET /` and `/index.html`, and all API endpoints): verify that the request contains the valid session token either in the `Authorization` header (`Bearer <token>`) or as a query parameter `?token=<token>`. Return `401 Unauthorized` for mismatched tokens. Access the authorization header case-insensitively using `req.headers.authorization`.
   - Implement SSE (Server-Sent Events) endpoint at `GET /api/events`:
     - Keep connection open without timeouts by setting `req.socket.setKeepAlive(true)` and `req.socket.setTimeout(0)`.
     - Disable proxies/caching by setting response headers:
       - `Content-Type: text/event-stream`
       - `Cache-Control: no-cache, no-transform`
       - `Connection: keep-alive`
     - Maintain an active registry of client responses.
     - Clean up connections by listening to the request's `close` event, preventing leaks and duplicate write attempts.
     - Immediately upon connection, push the complete current state (serialized and redacted) as the first event message using standard `data: <payload>\n\n` syntax to support reconnects.
     - Stream state changes to clients, ensuring the payload is filtered through `redactSecrets` to protect sensitive information:
       ```typescript
       const payload = redactSecrets(JSON.stringify(this.state));
       ```
     - Wrap individual client socket writes inside the broadcast state loop in a `try-catch` block and verify `res.writable && !res.writableEnded` to prevent process crashes if a browser tab is closed abruptly.
   - Implement unified action endpoint:
     - `POST /api/action`:
       - Buffer the incoming body chunks up to a 10KB limit. If exceeded, set a `limitBreached = true` flag, destroy the socket, and return `413 Payload Too Large`. Attach error listeners to the request stream.
       - Inside the `'end'` listener, if `limitBreached` is true, return immediately.
       - Parse the buffered JSON body inside a `try-catch` block. If parsing fails, return `400 Bad Request`.
       - JSON body format expects `{ action: 'approve' | 'reject' | 'retry' | 'override' | 'abort' | 'exit', comment?: string }`.
       - Validate that the `action` is one of the allowed values, returning `400 Bad Request` if invalid.
       - If a request is received and no resolver is active (except for `'exit'`), return `409 Conflict`.
       - If action is `'exit'`, resolve the exit confirmation promise.
       - Otherwise, resolve the pending approval promise with the action and custom comment.
     - `GET /api/state`: Returns the redacted current UI state.
   - Implement leak-free port-hunting:
     - To prevent `Server is not running` exceptions during EADDRINUSE close attempts, instantiate a **new** `http.Server` instance for each port bind attempt.
     - Listen to host `'127.0.0.1'` (localhost only, for network security).
     - Guard against port `0` ephemeral binding conflicts: if `startPort` is `0`, bypass the port-hunting loop and bind exactly once directly to let the OS assign a random free port.
     - On EADDRINUSE error for non-zero ports, try the next port (up to `startPort + 100` to prevent infinite loops/stack overflow). Clean up error listeners on successful bind.
     - If no ports are available, throw an explicit error.
     - Retrieve the active port dynamically from the listening server using `(this.server.address() as net.AddressInfo).port`. Expose a `getUrl()` method returning `http://127.0.0.1:<active_port>/?token=<token>`.
   - Launch the default browser pointing to the dynamic server URL asynchronously using non-blocking child process `exec` or `spawn` with double-quoted URL targets, wrapping execution in a try-catch and registering an `'error'` event listener on the spawned child process to log launch errors as warnings instead of crashing:
     - Windows (`win32`): `cmd /c start "" "http://127.0.0.1:<port>/?token=<token>"`
     - macOS (`darwin`): `open "http://127.0.0.1:<port>/?token=<token>"`
     - Linux/other: `xdg-open "http://127.0.0.1:<port>/?token=<token>"`
     - Disable auto-launch via an option `autoOpenBrowser` during tests.
   - Implement `close()` method:
     - Check if `this.server` is defined and `this.server.listening` is true. If actively listening:
       - Iterate over the registry of active SSE client responses and call `res.end()` on each response stream to terminate connections.
       - Call `(this.server as any).closeAllConnections()` (safely typecheck it first using `typeof (this.server as any).closeAllConnections === 'function'`) to forcefully close all active HTTP keep-alive connections.
       - Return a Promise wrapping `this.server.close()` to ensure the event loop releases cleanly without throwing exceptions.
       - If not listening, resolve immediately to avoid `Server is not running` exceptions.

## 2. Technical Decisions & Core Node.js Implementation

### A. Non-Blocking Event Loop
To stream live verification stdout/stderr chunks to the UI without freezing the server:
- `cp.spawn` stdout/stderr streams are piped to the UI:
  ```typescript
  const child = cp.spawn('docker', args, { cwd, env });
  child.stdout.on('data', (data) => {
    stdout += data.toString();
    if (onChunk) onChunk(data.toString(), 'stdout');
  });
  ```

### B. CSRF Protection
A token is appended to the browser launch URL: `http://127.0.0.1:3000/?token=<token>`.
The frontend extracts this token and attaches it to SSE connections and fetch requests:
```javascript
const token = new URLSearchParams(window.location.search).get('token');
const eventSource = new EventSource(`/api/events?token=${token}`);
```

### C. Clean Stdin Listener Hook
When waiting for user exit/stop confirmation in `runTask`, we will clean up the stdin readline interface to prevent process leaks:
```typescript
async function waitForExitAcknowledgment(uiServer: UIServer): Promise<void> {
  let rl: readline.Interface | null = null;
  const cliPrompt = new Promise<void>((resolve) => {
    rl = readline.createInterface({
      input: process.stdin,
      output: process.stdout
    });
    rl.on('line', () => {
      resolve();
    });
  });
  await Promise.race([
    uiServer.waitForExitConfirmation(),
    cliPrompt
  ]);
  if (rl) {
    rl.close();
  }
}
```
